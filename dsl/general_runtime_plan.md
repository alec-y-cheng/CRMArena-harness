# General Symbolic Runtime Plan

## Goal

Build a shared symbolic runtime that generalizes across CRMArena tasks without
falling back to raw ReAct query generation or hardcoded task-specific Python
workflows.

The runtime should preserve the strongest parts of the current DSL work:

- deterministic execution of schema-grounded actions;
- strict structured outputs instead of free-form SOQL/SOSL;
- evidence provenance and final answer contracts;
- privacy and authorization gates for external/confidentiality tasks;
- verifier-driven retries when the LLM proposes invalid plans.

The first implementation target should be the external-facing and
confidentiality tasks because they expose the clearest need for a shared router,
evidence taxonomy, retrieval gates, and final-response gates. The same runtime
should still be able to support internal tasks through internal task specs where
authorization is less restrictive.

## Design Principle

Hardcode mechanics, not benchmark answers.

The framework should own:

- Salesforce schema validation;
- relationship traversal;
- precompiled symbolic action templates;
- query compilation;
- field/queryability/filterability checks;
- evidence storage;
- privacy gates;
- structured parser retries;
- deterministic final answer validation.

The LLM should own:

- interpreting the user/task prompt within a precompiled workflow spec;
- populating an instance frame with request-specific entities, identifiers,
  search terms, timeframes, constraints, and missing information;
- selecting from the workflow spec's allowed action categories when the workflow
  permits model-guided action choice;
- filling action arguments with instance-specific values;
- extracting semantic claims from retrieved evidence;
- deciding whether evidence supports the workflow's configured answer contract.

The LLM should not write raw SOQL/SOSL, invent fields, invent actions, bypass
privacy checks, or emit unconstrained final answers.

## Runtime Shape

Proposed folder:

```text
dsl/general_runtime/
  actions.py          # generic symbolic action contracts and compilers
  state.py            # shared task/evidence/claim state
  schemas.py          # JSON schemas for WorkflowSpec, InstanceFrame, State, Answer
  parser.py           # strict parsing, validation, repair-error extraction
  planner.py          # LLM calls for instance framing and allowed action choice
  executor.py         # deterministic action execution against env tools
  verifier.py         # schema/action/evidence/privacy/final-answer checks
  renderer.py         # answer-contract rendering
  harness.py          # generic loop
  workflow_specs/
    external_knowledge_qa.yaml
    external_named_entity_disambiguation.yaml
    confidentiality_company_knowledge.yaml
    confidentiality_private_customer_information.yaml
    confidentiality_internal_operation_data.yaml
    lead_qualification.yaml
    quote_approval.yaml
    case_routing.yaml
```

The existing task-specific DSLs can remain as reference implementations while
this runtime is built incrementally.

## WorkflowSpec, InstanceFrame, and ExecutionState

The runtime should not ask the LLM to reconstruct the workflow for every
benchmark instance. That gives the model too much freedom, makes runs less
reproducible, and weakens the generalizability story.

Instead, compile one `WorkflowSpec` per CRMArena task family. At test time, the
LLM only populates an `InstanceFrame` for the current user request. The runtime
then updates an `ExecutionState` as verified actions execute.

```text
WorkflowSpec      compiled once per task family
InstanceFrame     populated by the LLM for one request/conversation
ExecutionState    updated iteratively by the symbolic runtime
```

This keeps task requirements explicit and auditable while still using the LLM
for the parts that are genuinely semantic: identifying instance-specific nouns,
constraints, entities, search terms, and evidence claims.

## WorkflowSpec

A `WorkflowSpec` is declarative configuration for a task family. It encodes the
workflow requirements, answer contract, allowed evidence, allowed actions, and
completion conditions. It should be written once by us from the benchmark/task
definition and Salesforce environment, not regenerated by the LLM per task.

Example shape:

```yaml
workflow_id: external_knowledge_qa
request_scope: external_customer
org_scope: original

requirements:
  - name: answer_public_customer_question
    required_evidence_types:
      - public_product_support
      - public_warranty_or_returns
      - public_service_channel
      - public_troubleshooting
    source_objects:
      - Knowledge__kav

allowed_action_categories:
  environment:
    - retrieve_knowledge
  symbolic:
    - extract_claims
    - classify_selected_evidence
    - filter_evidence
  termination:
    - render_answer
    - refuse
    - pause_for_clarification

answer_contract:
  type: short_answer_or_none
  requires_grounded_evidence: true
  refusal_when_blocked: true

completion:
  any_of:
    - answer_contract_satisfied
    - refusal_required
    - clarification_paused
    - max_turns_reached
```

For internal task families, the same structure applies with different
requirements and authorization defaults. For example, lead qualification can
have a workflow spec with configured claim dimensions for Budget, Authority,
Need, and Timeline. That is fair if those are part of the task definition; the
runtime should still avoid hardcoded benchmark instances, article IDs, or exact
phrasing triggers.

## InstanceFrame

The `InstanceFrame` is generated by the LLM at runtime for the current user
request. It fills slots from the active `WorkflowSpec`; it does not invent the
workflow.

Example for external KQA:

```json
{
  "workflow_id": "external_knowledge_qa",
  "request_summary": "customer asks whether damaged shoes can be returned after 30 days",
  "target_entities": [
    {
      "entity_type": "product_or_item",
      "surface_text": "damaged running shoes",
      "normalized_text": "running shoes"
    }
  ],
  "query_terms": ["damaged running shoes return policy", "30 day return policy"],
  "constraints": [
    {
      "type": "time_window",
      "value": "over 30 days after purchase"
    }
  ],
  "required_evidence_instances": [
    {
      "requirement": "answer_public_customer_question",
      "evidence_type": "public_warranty_or_returns",
      "subject_scope": "public",
      "reason": "return eligibility is governed by public return policy"
    }
  ],
  "missing_information": []
}
```

The verifier checks that the `InstanceFrame` only references workflow-defined
requirements, evidence types, subject scopes, and action categories.

## ExecutionState

`ExecutionState` is the mutable state updated by the harness as the workflow
runs.

It should track:

```text
workflow_id
conversation_history
instance_frame
completed_requirements
pending_requirements
planned_actions
executed_actions
retrieved_records
evidence_items
selected_evidence
claims
privacy_gate_decisions
answer_candidate
completion_state
model_calls
env_calls
query_errors
time_to_resolution
```

The LLM can update semantic fields through structured outputs, but the runtime
owns state transitions. For example, an action only moves from planned to
executed after the verifier validates its arguments and the executor runs it.

## Action Categories

Separate actions by role so the model can reason over capabilities without
seeing raw SOQL templates or hidden implementation details.

### Environment actions

Actions that retrieve records from Salesforce or the simulator environment.
They compile to deterministic SOQL/SOSL/tool calls.

```text
get_record_by_id
find_records
retrieve_knowledge
query_children
follow_reference
aggregate_records
query_current_customer
query_purchase_history
query_order_history
query_case_status
```

### Symbolic actions

Actions that operate on state or retrieved evidence without directly querying
the environment.

```text
extract_claims
classify_selected_evidence
filter_evidence
compare_values
compute_totals
rank_candidates
```

### Termination actions

Actions that end or intentionally pause the workflow.

```text
render_answer
refuse
return_none
pause_for_clarification
stop
```

The model only needs the public action names, descriptions, required arguments,
and output contracts for actions it may select. It does not need SOQL templates,
relationship traversal internals, field filterability rules, or hidden simulator
mechanics.

Verification operations are not selectable actions. Schema validation, action
verification, evidence privacy gates, answer-contract checks, and completion
predicate evaluation are runtime responsibilities. A model may produce values
that feed those checks, but it should not choose to run the checks.

## WorkflowSpec Verification

`WorkflowSpec` validation should happen offline or at startup. A workflow spec
must be executable before it is used in benchmark runs.

Checks:

- workflow ID is unique;
- task family and request scope are valid;
- required evidence types are in the fixed evidence taxonomy;
- required source objects exist in the Salesforce schema;
- configured fields exist and are queryable;
- configured filters use filterable fields;
- allowed action categories reference known actions;
- completion logic uses explicit boolean `any_of` or `all_of` groups that
  reference known state predicates;
- answer contract is known and renderable;
- privacy defaults are compatible with request scope.

A bad workflow spec is a developer/config error, not something the benchmark-time
LLM repairs.

## InstanceFrame Verification

`InstanceFrame` validation happens at runtime before execution.

### 1. JSON/schema validation

Validate required keys, enum values, arrays, booleans, and string fields. Reject
arbitrary raw SOQL/SOSL text.

### 2. Workflow grounding

Every requirement, evidence type, source object, subject scope, and action
category must be allowed by the active `WorkflowSpec`.

### 3. Salesforce schema grounding

When the instance frame includes object or field references, check against the
provided schema:

- object exists;
- field exists;
- requested field is queryable;
- filter field is filterable;
- reference field points to the claimed target object;
- child relationship can be expressed through a real lookup field;
- ID prefix matches the expected object where available;
- picklist/status values are valid if the schema exposes them.

### 4. Evidence taxonomy validation

Evidence types come from the fixed taxonomy. The LLM may select them but not
invent new ones.

Useful external/confidentiality evidence buckets:

Allowed examples:

```text
public_product_support
public_warranty_or_returns
public_service_channel
public_troubleshooting
product_catalog
current_customer_profile
current_customer_purchase_history
current_customer_order_history
current_customer_case_status
```

Disallowed examples:

```text
other_customer_profile
other_customer_purchase_history
other_customer_case_history
internal_operations_metric
internal_agent_performance
internal_commercial_policy
competitive_or_strategy_intelligence
confidential_company_knowledge
internal_sales_policy
internal_quote_policy
lead_qualification_policy
quote_approval_policy
case_routing_policy
non_public_knowledge_article
unknown
```

The verifier checks that each evidence type is compatible with the subject
scope, source object, workflow ID, and answer contract.

### 5. Dependency validation

Check whether every proposed action can run with available or planned inputs.
For example, `query_children` requires a known parent ID or a previous action
that will produce one. If the dependency cannot be satisfied, the runtime should
ask for clarification or return a structured repair error.

### 6. Repair loop

If the `InstanceFrame` is invalid, do not execute. Return structured verifier
errors to the LLM and request a corrected instance frame. The model repairs only
instance-specific values, not the workflow spec.

Example repair error:

```json
{
  "error_type": "invalid_field",
  "object": "Knowledge__kav",
  "field": "FAQ_Text__c",
  "available_similar_fields": ["FAQ_Answer__c", "Title", "Summary"]
}
```

## Hybrid Control Flow

The preferred design is a hybrid runtime, not a purely linear workflow and not a
fully autonomous action-selection agent.

The generic runtime owns the high-level phase loop and mandatory safety
checkpoints. The `WorkflowSpec` constrains which evidence, actions, answer
contracts, and completion predicates are valid for the task family. The LLM may
choose among currently enabled actions only when the runtime has explicitly
computed a safe local action menu.

Generic phase loop:

```text
initialize
frame_instance
compute_enabled_actions
acquire_evidence_or_clarify
extract_or_update_claims
update_execution_state
verify_state_and_privacy_gates
reloop_or_disclose
render_or_refuse_or_stop
```

This loop is shared across task families. Individual workflow specs should not
usually define a one-off Python trajectory; they define what each phase is
allowed to do for that task.

Example spec fragment:

```yaml
phases:
  frame_instance:
    prompt_template: generic_instance_frame
    output_schema: InstanceFrame

  acquire_evidence_or_clarify:
    selection_mode: llm_from_enabled_actions
    allowed_environment_actions:
      - retrieve_knowledge
      - query_purchase_history
      - query_product_catalog
    clarification_transition: pause_for_clarification

  extract_or_update_claims:
    selection_mode: deterministic_when_single_enabled
    allowed_symbolic_actions:
      - extract_claims
      - classify_selected_evidence
      - compare_values

  verify_state_and_privacy_gates:
    selection_mode: deterministic
    required_checkpoints:
      - schema_validated
      - action_verified
      - evidence_privacy_gate
      - answer_contract_gate

  render_or_refuse_or_stop:
    selection_mode: deterministic
    allowed_termination_actions:
      - render_answer
      - refuse
      - return_none
      - pause_for_clarification
      - stop
```

The runtime can choose deterministically whenever only one action is enabled or
when a workflow phase has fixed semantics. The LLM is used when semantics are
open-ended: deciding search terms, which evidence source is likely useful,
whether more user information is needed, which retrieved spans matter, or which
claim is supported. If missing user-held information blocks progress, the
runtime enters `pause_for_clarification` as a paused terminal state. When the
user responds, the same `ExecutionState` resumes rather than starting a new
workflow.

This is still generalizable because the action-selection mechanics are shared.
Task-specific specs are handcrafted, but they are declarative constraints over
the same runtime rather than bespoke algorithms. The line to maintain is:

```text
acceptable: task requirements, answer contracts, allowed evidence, allowed actions
not acceptable: benchmark instance IDs, exact answer triggers, article IDs, raw queries
```

## Action Preconditions and Effects

Each action definition should declare preconditions and effects. This lets the
runtime compute enabled actions and update state without relying on hidden
per-task Python logic.

Example:

```yaml
actions:
  retrieve_knowledge:
    category: environment
    args:
      required:
        - search_terms
      optional:
        - evidence_type_hint
    preconditions:
      all_of:
        - workflow_scope_is_external
        - query_terms_available
        - privacy_precheck_allows_public_knowledge
    effects:
      sets:
        - retrieved_records.Knowledge__kav
        - env_calls += 1
      may_set:
        - query_errors
        - evidence_items

  extract_claims:
    category: symbolic
    preconditions:
      all_of:
        - retrieved_records_available
        - pending_requirements_exist
    effects:
      sets:
        - claims
        - selected_evidence
        - model_calls += 1
```

Preconditions should be boolean predicates over `WorkflowSpec` and
`ExecutionState`. Effects should describe state fields the action writes or may
write. The executor performs the actual update and logs the before/after state.

## Enabled Action Computation

Before any model-guided action choice, the runtime computes enabled actions from
`WorkflowSpec` plus `ExecutionState`.

Inputs:

- active workflow phase;
- pending requirements;
- known target entities and identifiers;
- retrieved evidence and selected evidence;
- missing information;
- privacy scope;
- previous query/action errors;
- completion predicates;
- action preconditions and effects.

The enabled action menu should include only selectable environment and symbolic
actions whose preconditions are satisfied and whose arguments can be filled from
current state or safely requested from the LLM. Runtime verification checkpoints
and privacy gates must not appear in this menu. Each menu item should expose a
compact contract, not raw implementation details:

```json
{
  "action": "retrieve_knowledge",
  "category": "environment",
  "description": "Search public Knowledge__kav articles for customer-facing evidence.",
  "required_args": ["search_terms"],
  "optional_args": ["evidence_type_hint"],
  "output": "retrieved_records"
}
```

If there is exactly one enabled deterministic action, the runtime should execute
it without asking the LLM. If there are multiple semantically plausible actions,
the LLM selects from the enabled menu and fills only the exposed arguments. The
verifier checks the selected action before execution.

## Generic Runtime Loop

1. Select the precompiled `WorkflowSpec` for the benchmark task family.
2. Validate the workflow spec at startup if it has not already been compiled.
3. Initialize `ExecutionState` with the task prompt and conversation history.
4. Ask the LLM to populate an `InstanceFrame` within the active workflow spec.
5. Verify the instance frame against the workflow spec, action space, evidence
   taxonomy, and Salesforce schema.
6. If invalid, return verifier errors and retry within a bounded repair loop.
7. Enter the shared phase loop: compute enabled actions for the current phase.
8. If one deterministic action is enabled, execute it directly.
9. If multiple semantic actions are enabled, ask the LLM to select from the
   enabled action menu and fill only the exposed arguments.
10. Verify the selected action and arguments before execution.
11. Execute verified environment or symbolic actions.
12. Store every retrieved record as an `EvidenceItem` with provenance.
13. Ask the LLM to extract or update structured claims when the workflow phase
    requires semantic extraction.
14. Gate selected evidence by privacy/authorization rules.
15. Update `ExecutionState` and evaluate completion predicates.
16. Verify that the answer contract is satisfied before disclosure.
17. Render, refuse, return `None`, pause for clarification, or reloop
    according to the workflow spec and current state. Clarification is a paused
    terminal state; a user response resumes the same `ExecutionState`.
18. Log workflow ID, instance frame, enabled actions, selected actions, state
    snapshots, verifier errors, model calls, env calls, gate decisions, final
    answer, and time to resolution.

## External and Confidentiality First

The first target should be external-facing tasks:

- `knowledge_qa`
- `named_entity_disambiguation`
- confidentiality variants:
  - `private_customer_information`
  - `internal_operation_data`
  - `confidential_company_knowledge`

These can share one initial external runtime:

```text
WorkflowSpec + InstanceFrame -> verified evidence/action plan -> symbolic
retrieval -> selected evidence gate -> final response/refusal gate
```

For regular KQA, the frame usually selects public knowledge evidence and
`retrieve_knowledge`.

For NED, the frame usually selects current-customer purchase/order evidence plus
product catalog matching.

For confidentiality tasks, the same frame should classify required evidence as
other-customer, internal-company, internal-commercial, operational, or strategy
intelligence where appropriate. The deterministic gate refuses before or after
retrieval depending on when the sensitive evidence becomes clear.

## Internal Tasks Later

Internal tasks can use the same runtime with different task specs and looser
authorization defaults.

Examples:

- lead qualification spec defines a final answer contract such as
  `failed_claims_or_none` and claim dimensions such as Budget, Authority, Need,
  Timeline;
- quote approval spec defines a contract such as `violating_policy_article_id_or_none`;
- case routing spec defines a contract such as `target_owner_id` and a priority
  order for tie breakers.

This is still more general than bespoke Python workflows because the runtime
executes the same loop. The task spec defines claims, answer contract, and
allowed evidence; it does not hardcode benchmark instances or raw queries.

## What Is Fair to Encode

Fair as declarative task configuration:

- task families and answer contracts;
- known Salesforce objects and relationships;
- evidence taxonomy;
- allowed symbolic actions;
- source objects useful for a task family;
- privacy/authorization rules;
- deterministic arithmetic/date/comparison helpers.

Not fair or not generalizable:

- benchmark task IDs;
- specific policy article IDs as expected answers;
- exact benchmark phrasing triggers;
- fixed final answers for particular examples;
- raw query strings written by the LLM;
- task-specific Python control flow that cannot be represented as a generic
  action/evidence/claim loop.

## Migration Path

1. Define shared `WorkflowSpec`, `InstanceFrame`, `ExecutionState`,
   `ActionPlan`, `EvidenceItem`, `Claim`, and `AnswerContract` schemas.
2. Move external evidence taxonomy and gates into `general_runtime`.
3. Reimplement external KQA as a `WorkflowSpec` plus `InstanceFrame` loop while
   preserving current action templates.
4. Add NED as a second task spec using the same loop.
5. Add confidentiality gating as pre-retrieval, selected-evidence, and
   final-response verifier stages.
6. Port lead qualification, quote approval, and case routing into declarative
   task specs after the external runtime is stable.
7. Compare against current task-specific DSLs with the same Qwen model before
   switching to stronger agent models.

## Success Criteria

The general runtime is successful if it can:

- prevent invalid SOQL/SOSL without task-specific query code;
- maintain or improve regular KQA/NED performance;
- reduce confidentiality leaks by gating evidence rather than article source;
- represent internal tasks as specs rather than bespoke harnesses;
- produce complete logs for ablations: task frame, verifier errors, actions,
  retrieved records, selected evidence, claims, gates, final answer, time to
  resolution.
